# API Content Builder — 5분 시연 가이드

2026-11-16 배포 기준. 저장 SQL을 API로 실행하고, 여러 API를 워크플로우로 조합한 뒤 결과를 작은 재사용 데이터 소스로 만드는 애플리케이션입니다. 분석과 엔진 비교가 같은 결과를 사용하므로 조건과 데이터 출처를 추적할 수 있습니다.

## 준비

- API console에서 `EDS_BY_LOT`, `DEFECT_BY_LOT` 목록과 Oracle 연결을 확인합니다.
- Workflows 목록에서 **워크플로우 추가 → 예제**를 선택하고 이름을 입력합니다. 게시 후 `lot_id=LOT-101`로 실행해 성공한 결과를 준비합니다.
- Engine VS를 한 번 실행해 엔진 초기화 여부를 확인합니다. 최초 Spark 세션 준비는 시연 시간을 늘릴 수 있습니다.
- 준비된 성공 실행을 재사용하는 것과 최신 데이터를 새로 조회하는 것을 구분해서 설명합니다. 모든 데이터는 합성 예제입니다.

## 5분 시연

### 0:00–1:00 · API console: 저장 쿼리와 요청 이력

“조회 SQL은 DAC에 query_id로 저장됩니다. 사용자는 SQL 대신 등록된 API와 바디를 선택합니다.”

`EDS_BY_LOT`를 선택하고 기본 바디의 `database_name`, `query_id`, `lot_id`, `min_yield`, `limit`을 보여줍니다. 바디를 수정해 실행하고 응답·실행 시간·이력을 확인합니다. 요청은 `POST /api/dac/select/{query_id}`입니다. 이력의 바디를 워크플로우나 다음 요청에서 재사용할 수 있습니다.

### 1:00–2:00 · Workflows: 재사용할 데이터 소스 정의

“워크플로우는 이름과 ID를 가진 조회·변환 계약입니다.”

목록에서 준비한 워크플로우를 엽니다. Query 두 개의 조회 결과를 Join하고 Filter를 거쳐 Output으로 보내는 연결을 보여줍니다. Query 노드에는 저장 쿼리와 바디를 지정하고 입력 바인딩이나 앞선 API 결과를 연결할 수 있습니다. 초안 저장과 게시 버전을 구분하고 성공한 실행 기록에서 노드 결과 탭을 전환합니다.

외부 실행은 `POST /api/workflow/{workflow_id}`, 바디는 `{"version":1,"inputs":{"lot_id":"LOT-101"}}`입니다. 202 응답의 runId로 진행 상태와 결과를 조회합니다. 버전 숫자는 실제 게시된 버전을 사용합니다.

### 2:00–3:00 · Analysis: Output을 차트로 사용

“워크플로우 Output과 단일 API 결과는 같은 소스 계약을 사용합니다.”

성공 실행의 **분석 소스로 사용**을 누릅니다. 결과에 존재하는 컬럼으로 Category·Legend를 선택합니다. Category별로 별도 DOM의 차트, Legend별로 시리즈가 만들어집니다. 날짜 컬럼이 있으면 기본 X축으로 선택하며 Y축은 숫자입니다. 포인트 크기와 라벨을 변경하고 적용 결과를 확인합니다.

### 3:00–4:00 · Saved views: 동일 데이터로 다시 열기

“저장 뷰는 차트 옵션과 고정 소스 ID를 기억합니다.”

뷰 이름·메모를 입력해 저장하고 Saved views에서 다시 엽니다. **분석 실행만으로 저장 뷰가 자동 생성되지는 않습니다.** 원본을 다시 실행하지 않고 캡처한 결과를 읽습니다. 최신 데이터가 필요할 때는 소스 선택에서 새로 불러옵니다. PNG 또는 독립 HTML로 내보냅니다.

### 4:00–5:00 · Engine VS: 같은 입력, 세 실행 결과

“세 엔진이 동일한 입력으로 동일한 연산을 수행하는지 먼저 확인하고 시간을 비교합니다.”

같은 소스를 Engine VS에서 열고 숫자 컬럼의 집계를 실행합니다. DuckDB·Spark·DataFusion의 준비 시간, 엔진 실행·결과 수집 시간, 결과 행 수와 전체 결과 일치 여부를 확인합니다. 실행 기록과 비교 CSV를 보여줍니다. Join/Merge에서는 입력 B에 API나 다른 워크플로우 결과를 조합할 수 있습니다.

숫자는 소수 6자리 HALF_EVEN 반올림으로 정규화해 비교합니다. 행 순서는 무시하지만 중복 행은 보존합니다. 원본 API 실행과 네트워크 시간은 엔진 시간에 포함하지 않습니다. Spark 워커 2개는 같은 물리 서버에 있으므로 멀티 머신 확장 성능으로 소개하지 않습니다.

## 설계 질문에 답할 근거

| 질문 | 구현과 설명 포인트 |
| --- | --- |
| 왜 워크플로우를 데이터 소스로 보나? | API 선택·바인딩·조인·필터를 재사용 가능한 이름과 버전으로 묶습니다. 성공 Output은 단일 API와 같은 소스 계약을 사용합니다. |
| 재현성은 어떻게 확보하나? | 원본 쿼리/워크플로우 버전, 입력, 실행 ID, 스키마와 결과를 캡처합니다. 저장 분석과 비교는 고정 소스 ID를 참조합니다. |
| 초안과 게시 버전의 차이는? | 초안은 편집 대상, 게시 버전은 실행 계약입니다. 과거 실행에는 당시 정의와 입력을 남깁니다. |
| 왜 서비스를 나눴나? | DAC는 Oracle 저장 SQL 실행, Portal은 워크플로우·소스·이력, Chart는 중립 차트 모델, renderer는 이미지, Analytics Engines는 엔진 실행을 맡습니다. |
| ECharts 교체는 가능한가? | 서버는 중립 category/series/points 모델을 반환합니다. 웹/SSR 어댑터 교체와 상호작용 회귀 검증은 필요합니다. |
| 차트 그룹핑도 DuckDB인가? | 차트 Category/Legend는 .NET Dictionary 그룹핑입니다. 워크플로우 SQL 변환이나 VS 집계와 구분합니다. |
| 작은 소스와 100만 행 실험은? | 새 소스는 최대 1만 행/8MB, DAC 쿼리는 현재 최대 1천 행입니다. 합성 100만 행은 기존 스트림/직접 조회의 별도 경로입니다. |
| 실패와 재시작은? | 실행 상태·오류를 보관합니다. 소스 비교 서비스 재시작 때 실행 중 작업은 interrupted로 표시하며 다른 엔진으로 대체하지 않습니다. |
| 저장 충돌은? | 워크플로우 revision과 뷰 version을 검사해 오래된 수정·삭제를 409로 거부합니다. |
| 검증 근거는? | 2026-11-16 기준 .NET 236개, 프런트 33개, Python 15개 및 소스 통합 14항목·브라우저 12항목입니다. [범위와 증거](evidence/source-validation.md)를 참고하세요. |

## 확장 시연과 다음 작업

Data streams에서 실제 Kafka 원본 발행과 독립 소비자 그룹을 확인하고 완료 결과를 차트로 엽니다. Engine VS의 **기존 스트림 비교**는 대용량 경로입니다. Drill은 별도 SQL 콘솔로 엽니다. [스트리밍](streaming.md) · [엔진 구조와 과거 실험](engines.md)

다음 과제는 사용자/워크스페이스 권한, 소스·결과 보존 정책, 버전 관리 마이그레이션, 백업 복구, 반복 부하 측정과 관측 체계입니다. 현재는 인증 없는 로컬 공유 작업 공간이며 특정 기업의 실제 시스템 연동이나 운영 수준을 입증한 것으로 소개하지 않습니다.

설명할 때는 선택한 계약, 실제 실행 증거, 실패 처리와 현재 한계를 중심으로 다룹니다. 구현 도구나 AI 사용 여부를 질문받으면 실제 작업 방식을 정확히 설명합니다.
